# Set up a team by hand

Two small files, one minute.

1. Install the plugin (the install commands in the [README](../README.md#get-started)). Claude Code puts the `teamrig` command on the path of each session's Bash and PowerShell tools.
2. Describe your team in `~/.teamrig/teams/<team>/config.json`:
   ```json
   { "configVersion": 8, "sessions": ["lead", "api", "web", "data"], "roles": { "lead": "lead" } }
   ```
3. Tie your project to the team: put `{"team": "<team>"}` in a `.teamrig.json` at the project's root. It names a team
   on your machine only, so keep it out of git: add the line `.teamrig.json` to the repository's `.git/info/exclude`.
4. Start one Claude Code tab per session, telling each its name, for example `TEAMRIG_SESSION=web claude`
   (PowerShell: `$env:TEAMRIG_SESSION='web'; claude`).

`teamrig team create <team> --sessions <id,id>` does steps 2 and 3 for you, and `teamrig open <session>` opens a tab
for a session (step 4).

Permissions: in auto mode every `teamrig` command runs with no settings entry. In default mode, Claude Code asks
before each one unless you add `"Bash(teamrig:*)"` to `permissions.allow` in `~/.claude/settings.json` or the
project's `.claude/settings.json` ([what was tested](../plugins/teamrig/skills/teamrig-guide/hooks.md#permissions)).

## Configuration

This table says where each setting lives; [every config key](configuration.md) lists each key of the team config with
its type, default and meaning.

| Setting | Where | Default |
| --- | --- | --- |
| Kit home (teams and their state) | `$TEAMRIG_HOME` | `~/.teamrig` |
| The team | `$TEAMRIG_TEAM`, else the nearest `.teamrig.json` above the current folder, else above `$CLAUDE_PROJECT_DIR` | none |
| The session | `--session <id or name>` on a command, else `$TEAMRIG_SESSION` | none |
| Team members and roles | `<kit home>/teams/<team>/config.json` | none |
| Sub-leads | `leads` in the team config (since 0.132.0), written by `teamrig promote` and `demote`: each sub-lead's members, by id; the lead leads every session no list names, and a sub-lead may list sub-leads. A member's decision and approval waits may name its sub-lead | none: the lead leads everyone |
| Automatic archiving of the task list | `register.autoArchive` in the team config: `false` stops writes from archiving it; `teamrig compact` still does by hand | on: after the first `compact`, a write past 512 KiB of log archives it and says so in a NOTE line |
| Task descriptions | `register.requireDescription` in the team config (since 0.44.0): `false` lets `add` go without `--description` and lets `update --description none` clear one | on: `add` needs a description |
| The verify loop | `register` in the team config: `requireProofOnVerifying` (`false`: a note naming the proof is enough, and no `--waits` saying when it runs), `verifyGate` (`warn` lets a start that needs a verifying task, or a first start while the session's own verify steps are due, through with a warning), `maxVerifying` (the verifying tasks a session may hold before its oldest are due and `PILE-UP` flags them; `0` turns both off), `maxReparks` (how many times in a row a proof may be put off to other waits before `set` refuses another and `REPARKED` flags it; `0` turns both off) | `true`, `refuse`, `5`, `2` |
| Decision cards | `register.requireDecisionCard` in the team config (since 0.79.0): `false` lets a wait on the owner's decision or approval go without a card, and `check` stops flagging `NO-CARD` | `true` |
| Owner decision batches | `decisions` in the team config (since 0.126.0): `batchTimesUtc` (the UTC times, `HH:MM`, the lead asks the owner a batch, such as its checkpoints), `batchAt` (how many waits not yet asked make a batch due before then; `0`: off) | no times (the daily meeting is the batch); 5 |
| Tab status | `tabStatus.enabled` in the team config (since 0.73.0), with `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` in Claude Code's `env` so it leaves the title to the hooks: a colored circle before each tab's title for what its session is doing | off |
| Turn log | `turnLog` in the team config (since 0.100.0): `enabled`, `keepHours` (1 to 168): each session's prompts and replies, secret shapes masked, kept for the task pane under `state/turn-log/` | on, 24 hours |
| Context refresh | `refresh` in the team config: `enabled`, `contextTokens`, `everyTasks`, `everyTasksMinTokens`, `tabTitle`, `autoRestart`, `restartDelaySeconds`, `endCommand` (these three since 0.37.0), `holdAfterActivityMinutes`, `countdownSeconds`, `compactCeilingTokens` (these three since 0.106.0), `handoverDir`, `handoverMaxBytes` (since 0.161.0) | on, at 120,000 tokens or every 3 tasks from 80,000, marks the tab, no automatic restart (on: 15 s after its turn ends), no end command, the mod's `/clear` held 5 min after your last key and counted 20 s down, compaction held up to 185,000 while a handover is due, `<team>/handover/`, a handover of at most 20,000 bytes |
| Hiring sessions | `hiring` in the team config (since 0.36.0): `policy` (`off`; `owner`: each `teamrig hire` needs `--approved-by`; `lead`; `automatic` since 0.45.0: the lead decides, and since 0.46.0 a hired session whose last open task closes is asked to retire itself, since 0.233.0 only to write its handover: a lead over it retires it), `idleHours` (config version 7, 0.233.0, dropped it: a hire is due to retire only once the burst it was hired for is over), `reviewDays` (since 0.233.0 `teamrig hire <id> --review` keeps a hired session to a new review day), and since 0.46.0 `resumeMaxTokens` and `resumeMaxIdleDays` (how small and recent a rehired session's last Claude Code session must be for `teamrig open --resume`), and since 0.79.0 `scaleOut` (`windowDays`, `minDone`, `topPriorities`: how `check`'s SCALE-OUT measures an area's pace and which dated work it counts); config version 4 dropped the fixed `dailyPct` and `maxDailyPct`: a hire's daily budget is its part of the team's; config version 6 (0.232.0) dropped `maxSessions` and `capRaisedBy`: no cap counts hires, `hire --yes` refuses only while the host has no room for one more tab | the owner approves each hire; review after 7 days; resume at most 250,000 tokens and 7 idle days; pace over 7 days once 3 are done, on the top 2 priorities |
| Bursts | `burst` in the team config (since 0.55.0): `policy` (`off`; `owner`: each `teamrig burst start` needs `--approved-by`; `lead`: the lead decides; no value starts one by itself), `surplusHours` (how long before the reset a surplus burst may start), `minSparePct` (the share of the week projected unused that makes one worth it), `maxHelpers` (the most helpers per session at once in a burst), `maxHires` (the most sessions the lead may hire for one) | the owner approves each burst; 48 hours; 5%; 3 helpers; 2 hires |
| Weekly token budget | `budget` in the team config: `enabled` adds the pacing sentence to the team rules, with `targetPct` and `reservePct`; `weeklyLimitW`, `reset`, `paceEndHoursBeforeReset`, `quietHours` and `sessions.<id>.share` set the pace line and each session's daily part; `weeklyLimitW` is a starting guess that the W per percent learned from the meter log replaces (since 0.136.0). The team's daily budget is never a fixed number: it is recomputed at every reading from what is left of the week and the active time to the reset, and config version 4 dropped the fixed `dailyPct` and `maxDailyPct`; `subagentWeight` (since 0.35.0) is what one W of a subagent costs in W of a main session. `lift.maxStopPct` and `lift.reserveStopPct` (since 0.9.0) bound the stop % of a leader's `teamrig budget lift`. The lead's `teamrig budget setup` (since 0.14.0) writes `enabled`, `overAction`, `escalate` and `quietHours`, with a preview first. A top-level block since 0.8.0: an older config's `coordinator.budget` is reported as moved | off; target 99.5%, reserve 0.5%; subagent weight 1; lifts stop by 99.3%, or 99.9% with `--reserve` in the last hour; nothing blocks or acts |
| Status line snapshots for `teamrig budget` | `budget.statusSnapshotDir` in the team config, relative to the team's folder; written by `teamrig statusline` once `teamrig statusline install` makes it Claude Code's status line, or by your own status line in the same format ([the status line](../plugins/teamrig/skills/teamrig-guide/requirements.md#the-status-line-optional)) | `<kit home>/usage/live` |
| What auto mode takes as true about the team | `autoMode.environment` in Claude Code's user settings, written by `teamrig automode install` (since 0.154.0) and taken out by `teamrig automode uninstall`: lines tagged `[teamrig <team>]` that name the protected branches, the register commands, what `queue` and `test` wrap, who removes a worktree, that a session may rebase its own branch and that editing a clean tracked file in its own worktree is not destruction; every other line stays ([the command](../plugins/teamrig/skills/teamrig-guide/commands.md#teamrig-automode-install)) | none: auto mode knows nothing of the team |
| The time zone people read and type times in | `timeZone` in the team config (since 0.101.0): an IANA name such as `Asia/Jerusalem`. teamrig shows every time in it, zone-marked (`09:00 IDT`), and reads a typed time (`--due`, `--waits time:`, `--since`) in it unless marked `UTC`; a stored time stays UTC, and a stored bare day is a day of this zone | the machine's own zone |
| Waking an idle session on urgent work | `wake` in the team config (since 0.53.0): `enabled`, `priority` (the least urgent priority that wakes a session, 1 to 5; p0 only while the session's budget holds it, past its daily budget with no room left in the team's day (the wake's own turn counted for both), or a short day pauses it (`budget.pauseByPriority`), and p0 and p1 only in quiet hours), `batchSeconds` (how long to gather tasks handed together, 0 to 3600), `minGapMinutes` (the least time between two wakes of one session, 0 to 1440), `dayStartUtc` (since 0.80.0: an `HH:MM` UTC outside the budget's quiet hours; from then each session with work it can start and no turn since gets one wake a day, and a burst wakes its sessions once it starts) | on: p1 (and p0) only, a 120 s batch, 15 minutes apart, no day start |
| Kept local rules | `ruleConflicts` in the team config (since 0.52.0), written by `teamrig rules keep` and `rules forget`: each local line the user keeps although it conflicts with a core rule (`file`, the line's `text`, the `rule` key, `wins`: `local` or `teamrig`, an optional `reason`); at most 40 | none: the core rules win |
| Pushes to protected branches | `pushGuard` in the team config: `protectedBranches` lists them (an empty list guards nothing); `pushToProtected` (since 0.11.0) set to `allow` lets a normal push through with a note instead of a question; set to `lead` (since 0.126.0) the lead's own push goes through, and another session's once a leader above it (the lead or a sub-lead) approved one of its waiting tasks (`teamrig approve`), else it is refused; set to `gated` (since 0.218.0) a hand push is cleared the same way, else refused with "Merge the branch with `teamrig merge` instead": merge merges a change that holds the self-merge gates (a live task of its own, a pass record of the rebased tree, commit sizes, a test changed with source, the repo's `reviewGate`) with no approval, and holds one that misses a gate for the session's leader. `commits.sourcePatterns` (at most 8 regular expressions over `/`-separated paths; by default code files by extension) are the paths that count as source for the tests gate. Force-push, mirror and delete stay refused; a `--force-with-lease` push and a command teamrig cannot read still ask. `reviewPaths` adds review entries (`{ "glob", "mode": "always" \| "check", "class": "security" \| "leader" }`) to teamrig's own, for the repos whose `delivery.repos` entry sets `reviewGate`: `teamrig merge` holds a change they hit until its reviewer approves it | `main` and `master`; `ask`; no `reviewPaths` |
| Skipped git hooks | `commitGuard` in the team config (since 0.92.0): `skipHooks` is `deny` (the default), `ask` or `allow` for a git command run without the repository's hooks (`--no-verify`, `git commit -n`, `HUSKY=0`, a `core.hooksPath` override) | `deny` |
| Hook questions | `prompts` in the team config (since 0.98.0): `hookAsks` is `ask` (the default) or `refuse`, which turns every permission question a teamrig hook would raise (a push to a protected branch, a push it cannot read, a skipped hook or ad-hoc run under `ask`, a held helper launch), and each permission prompt Claude Code would raise on its own but the question picker's and plan mode's exit (where, since 0.151.0, a provably read-only line runs and a line with a rerun form is refused quoting it; since 0.268.0 a line that runs one of the session's own jobs runs too, and `routeAllow`, `on` by default, lets five of them run before any permission check), into a refusal that tells the session to record the step as waiting for the owner's approval and take its next task | `ask` |
| Ad-hoc package runs | `packageGuard` in the team config (since 0.63.0): `adHocRunners` is `deny` (the default), `ask` or `allow` for a line that would fetch and run a package outside the project's lockfile (`npx` of a tool not installed, `npm create`, `pnpm dlx`, `yarn dlx`) | `deny` |
| Unvetted installs | `packageGuard` in the team config (since 0.112.0): `installs` is `deny` (the default), `ask` or `allow` for an install that names a version the public npm registry does not vouch for: published less than `cooldownDays` (0 to 365) days ago, with a known advisory, or not an exact version or dist-tag ([the package guard](../plugins/teamrig/skills/teamrig-guide/hooks.md#before-a-shell-command-the-package-guard)) | `deny`; 14 days |
| Secrets printed into a session | `secretGuard` in the team config (since 0.108.0): `secretReads` is `deny` (the default), `ask` or `allow` for a Bash, PowerShell, Read or Grep call that would print a secret file, the whole environment, a secret variable or a Kubernetes secret's data; `writes` (since 0.228.0) the same for a shell line that holds a secret as text and for a Write or Edit whose text holds one outside a secret file; `paths` (at most 32 globs) and `envNames` (at most 16 patterns) add the team's own, a `!` entry keeping one printable ([the secret guard](../plugins/teamrig/skills/teamrig-guide/hooks.md#before-a-shell-command-or-a-read-the-secret-guard)) | `deny` for both; no own paths or names |
| Privileged commands | `exec` in the team config (since 0.134.0): `path` lists the folders a request's bare program name is looked up on, in order, and is the only PATH its runs get (the session's own is never searched); `webhookEnv` names the variable that holds the security channel's webhook URL, never the URL, and each review and run is posted there. `roles.securityReviewer` names the session that reviews requests (a child team's may be `<team>/<id>` of a team above, who reviews with `exec ... --team <child>`); the owner always may ([privileged commands](../plugins/teamrig/skills/teamrig-guide/commands.md#privileged-commands)). On Windows, Node adds `HOMEDRIVE`, `HOMEPATH`, `LOGONSERVER`, `SYSTEMDRIVE`, `USERDOMAIN`, `USERNAME`, `USERPROFILE` and `WINDIR` to a run's environment when they are missing; none holds a secret | no path (a request names its program by absolute path); nothing posted; no reviewer (only the owner reviews) |
| Read-only shell lines without a prompt | `readonlyShell` in the team config (since 0.74.0): `enabled` lets a Bash or PowerShell line whose every command provably only reads run without a permission prompt; `allowPrefixes` (at most 16) lists commands trusted with any arguments by their leading words (`npx tsc --noEmit`), so leave out a tool whose flags write ([the read-only allow](../plugins/teamrig/skills/teamrig-guide/hooks.md#before-a-shell-command-the-read-only-allow)) | off; no prefixes |
| Picker guard | `pickerGuard.enabled` in the team config (since 0.90.0): refuses the question picker (`AskUserQuestion`) to every session, with the reason to decide it if it is the session's own, else record it on its task and go on; since 0.106.0 to every helper too, and to the lead outside the owner's daily meeting; since 0.196.0 in it too, unless `decisions.askWith` was `picker`; since 0.330.0 on unless a team sets it false, and in the meeting always, `decisions.askWith` dropped ([the picker guard](../plugins/teamrig/skills/teamrig-guide/hooks.md#before-a-question-the-picker-guard)) | on |
| GitHub issues imported as tasks | `github` in the team config: `repos` (`owner/name`, at most 20), `sessions` (a repository to the session that owns its issues), `owners` (a GitHub login to a session), `closedDays` (how far back closed issues are read) and `everyMinutes` (how often the hooks sync on their own; 0 = by hand only); `teamrig gh sync` reads them through `gh`, with the read-only token saved as `teamrig-gh-<owner>` when there is one, and never writes to GitHub ([GitHub sync](github-sync.md)). `$TEAMRIG_GITHUB=off` turns it off on one machine | off (no repos); `closedDays` 14, `everyMinutes` 15 |
| Where `teamrig open` opens a tab | `open.terminal` in the team config: `auto` (tmux inside tmux, else the platform's terminal), `tmux`, `windows-terminal`, `macos-terminal`, `gnome-terminal`, `konsole`, `x-terminal-emulator`, or `print` (prints the command to run) | `auto` |
| The room `teamrig open` and `hire --yes` need on the host | `open.headroom` in the team config (since 0.112.0): `sessionMb`, what a new session is counted at while none runs to measure (else the median running session's process tree), and `commitMaxPct`, the most of the commit limit the commit charge may reach with it; `floorMb`, what free memory must keep with it (unset: `delivery.queue.memoryFloorMb` plus `heavyReserveMb`); `loadMinutes`, how long a tab just opened holds its MB while it loads. The lead opens whatever the room. `closeIdleMinutes`: how long a session stays quiet before `teamrig close` may end it | `1200`, `92`, unset, `5`, `60` |

`teamrig config validate` reports a broken config; `teamrig config migrate` moves an older one to the current format.
A field teamrig cannot read is used at its default and writes are refused until it is fixed; a config from a newer
teamrig is read best-effort and never written. The other keys and their defaults are in
[the config schema](../plugins/teamrig/config.schema.json). The full command list is `teamrig help`, also in
[Every command](commands.md).
